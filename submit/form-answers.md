Project name
============================================================
fleet-voice-ops

============================================================
Elevator pitch(短い一文・タグライン)
============================================================
Ask from the kitchen — hear which of your parallel coding agents is stuck or
dead, and approve a safe resume by voice. Voice observability for agent fleets.

============================================================
Inspiration
============================================================
I run several coding agents in parallel. The failure mode I actually hit: I
walk away to cook, come back, and one agent has been waiting for my input for
30 minutes while another crashed silently. Checking a screen defeats the point
of stepping away — I wanted to ask out loud what was happening and get an
answer that respects the fact that I cannot look at a display.

============================================================
What it does
============================================================
fleet-voice-ops is a self-hosted MCP server that turns parallel coding-agent
sessions into a voice-queryable fleet:

- fleet_status — per-session liveness (active / stalled_suspect / dead) from
  PID liveness checks and last-activity timestamps — never conversation contents
- whats_stuck — the voice-first question "anything going on?" answered in one
  spoken sentence
- analyze_stall — the agentic part: multiple ranked hypotheses
  (waiting_on_human_input, blocked_by_unresolved_error, …), each with
  confidence and evidence signals, plus one recommended action
- request_resume — a write action behind human-in-the-loop voice approval:
  confirmation requires speaking the session name, never a number

The demo asks from the kitchen, hears one session waiting for input and one
dead, and approves resuming the dead session — no screen involved.

============================================================
How we built it
============================================================
Python MCP server over Streamable HTTP (mcp SDK 2.x, spec 2025-11-25) with a
Bearer auth middleware, verified end-to-end through an ngrok tunnel from a
generic MCP client. Session state comes from `devin list --format json`, PID
lock files, and transcript structure. All emitted fields pass a two-layer
allowlist — raw records contain titles and paths we read but never emit,
enforced by exact-key tests (16 tests total). The demo video itself is
generated by a deterministic pipeline: Piper neural TTS for narration plus
ffmpeg-rendered scene cards.

============================================================
Challenges we ran into
============================================================
- We assumed live sessions could be re-attached — measured reality: ACP
  rejects it. So resume targets dead sessions only, and the tool refuses live
  ones rather than corrupting state.
- Transcript file mtime lagged real activity by up to 24 minutes — we switched
  liveness to PID checks plus `devin list` activity timestamps.
- Raw session records mix sensitive fields (titles, paths) with safe ones, so
  "just don't read it" was impossible — we read internally and emit through an
  allowlist instead.

============================================================
Accomplishments that we're proud of
============================================================
- A voice round-trip that actually completes a write action: hear the state,
  speak the session name, approve the resume — all hands-free.
- Every claim in the demo is verified against real sessions and documented in
  the repo (reachability-evidence.md, interrupt-test-evidence.md).
- The demo video is itself reproducible: one command regenerates narration,
  scenes, and the verified final cut.

============================================================
What we learned
============================================================
Voice observability is different from voice control: knowing what to say —
which sessions are stalled, why, and what's safe to do next — is the product.
The Alexa+ submission path without partner tooling is real: a self-hosted
Streamable-HTTP MCP server plus a simulated voice loop covers the contract.

============================================================
What's next for fleet-voice-ops
============================================================
- Wire a real Alexa+ device once partner tooling opens beyond preview
- Move resume from dry-run to opt-in execution behind the same name-confirmation
  gate
- Grow hypothesis coverage from structure signals to outcome signals (PR
  merged, tests green) so "stuck" becomes "not progressing" detection

Open Source Mini Challenge — what you did / how it works / why it matters
============================================================
Created a new MIT-licensed open-source MCP server during the hackathon
window (first commit Oct 13, 2026). It turns parallel coding-agent sessions
into a voice-queryable fleet: four MCP tools (fleet_status, whats_stuck,
analyze_stall, request_resume) classify liveness from PID checks and
activity timestamps — never conversation contents — and gate the only
write action behind spoken session-name confirmation, dry-run by default.
It matters because parallel agent work is becoming common, but "what is my
fleet doing right now?" has no voice-first answer; the repo ships working
code, an allowlist-enforced privacy boundary, 16 tests, and a fully
reproducible demo-video pipeline so others can adapt the pattern.

Feedback Question 1: Which developer tools, APIs, and SDKs did you use and for what?
============================================================
- MCP Python SDK (mcp==2.3.0) — the whole product: a self-hosted MCP
  server over Streamable HTTP at spec 2025-11-25, exposing 4 tools.
- Alexa+ add-on developer docs (developer.amazon.com) — to understand what
  a self-hosted MCP server must look like to be Alexa+-compatible (auth
  surface, error responses, discovery).
- ngrok — public tunnel for end-to-end reachability testing from a generic
  MCP client.
- devin CLI — session metadata source (liveness/activity fields) for the
  agent fleet being observed.
- Piper TTS + ffmpeg — fully automated generation of the demo video.

============================================================
Feedback Question 2: For each tool, what worked well?
============================================================
- MCP SDK: the spec is readable and tool registration is declarative —
  zero to a serving endpoint in under an hour.
- Alexa+ docs: quickstart guides are concrete and code-forward.
- ngrok: reliable tunnel; end-to-end reachability was verified in minutes.
- Hackathon mechanics: product feedback being a required field makes
  friction-logging part of the artifact — excellent incentive design.

============================================================
Feedback Question 3: For each tool, what needs work?
============================================================
- MCP SDK: no documented spec-version ↔ SDK-class mapping; pinning the
  right Streamable HTTP surface took trial and error (Friction Log #1).
- Alexa+ docs: partner-only gating of the add-on CLI/Web Simulator is
  stated inconsistently across pages; some setup guides omit it entirely
  (Friction Log #2).
- Alexa+ add-on surface: a 401 returned without WWW-Authenticate is
  apparently intentional but non-obvious vs RFC conventions — a one-line
  callout would prevent misreads (Friction Log #3).
- Discoverability: @alexa-ai/addon-local-inspector is documented only
  inside specific guides, not on the main hackathon page (Friction Log #4).

============================================================
Feedback Question 4: How was your onboarding experience?
============================================================
- MCP SDK: fast for hello-world (working endpoint in under an hour),
  slower for transport details — had to read SDK source to confirm which
  helpers implement spec 2025-11-25.
- Alexa+ docs: good once you learn which parts are partner-gated; that
  learning itself took a wrong turn (see Friction Log #2).
- Overall: zero-to-working-prototype in one day; the slow part was
  discovering what is NOT available to hackathon entrants, not building.

============================================================
Feedback Question 5: Would you build with these devices and services again?
============================================================
Yes. The MCP standard is the right call — a self-hosted Streamable-HTTP
server is a clean contract that also works for non-Alexa clients, and the
"simulated Alexa+ experience" option made submission feasible without
partner access. We'd build again once the preview gating opens further;
the main ask is louder signage about what is gated (see Friction Log).
